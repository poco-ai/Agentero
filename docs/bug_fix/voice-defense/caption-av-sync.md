# 答辩间声音和字幕不同步

**状态**：已修复  
**日期**：2026-08-16  
**范围**：开场放声时机、舞台委员字幕揭示

## 现象

通话中委员在说前半句，字幕已经是整段问题；或字幕停在开头，扬声器已经问到后半句。2026-08-15 10:40 生产包一场：`10:41:08` 打断前奏，`10:41:18` 发出恢复指令，`10:41:23` 才 `playback enabled reason=gate`。用户从恢复开场的中段开始听见，同时舞台一次性铺开已积累的字幕。

## 根因

WebRTC 音轨是直播，字幕走 DataChannel，没有共享时间戳。开场门控为了挡住前奏，会把远端音轨和 `<audio>` 静音，直到字幕被判定为可接受开场。恢复指令发出后的那一轮本应从头听，却仍要等字幕证明，于是：

1. 扬声器接到的是当前 RTP（已经说到后半句）；
2. 舞台 `CaptionSlot` 底部锚定，一次写入整段字幕时看见的是句尾。

上游还会隔几秒吐一大截 ASR。即使开场之后，字幕也会整段抢到声音前面。`voiceState` 经常一直停在 `listening`，不能靠 `speaking` 当口型时钟。

## 修复

1. **恢复轮从头放声**：发出内部「请用「答辩现在开始。」…」之后立刻 `enableCommitteePlayback("recovery-turn")`。前奏仍然静音并打断；恢复指令之后的音频不再等字幕。
2. **舞台按语速揭示**：`VoiceCaptionPacer` 从该条委员字幕的首个 token（若更早收到 `speaking` 则从那时）按约 5 字/秒（中文）或 13 字符/秒（英文）往前走。迟到的大段 ASR 不会把可见结尾推过估计的口型位置。用户字幕、下一条委员发言和转写抽屉仍用全文。
3. **远端流到达时尊重已放声**：`onRemoteStream` 不再无条件把 `<audio>` 静音，避免恢复轮先放声、音轨后到时又被掐掉。
4. **能听见就出字幕**：恢复轮放声后，开场期不再把委员字幕当填充丢掉。否则扬声器已经在问，舞台仍停在「等待字幕」。流式小增量跟 ASR 走；只有一次铺开的大段才按语速节流。

不缓存整段远端 PCM，也不承诺卡拉 OK 逐字对齐。转写与复盘仍用未节流的全文。

## 后续：恢复立刻放声把残响和新开场叠在一起

第九轮「恢复指令一经发出就放声」修掉了中段起听，但又把 jitter buffer 里的前奏 PCM 和下一轮「答辩现在开始」叠到同一条音轨上。1 秒静置路径当时还不先 `stop_speaking`。舞台在新一轮 ASR 到达前是空的，用户听到的就是：第一句不是指定开场、两头一起说、有声无字。

旧 caption id 若在恢复发出后涨成「第一个问题」，还会写入 `openingAnnouncementId`，把真正的恢复开场当成重启撤回。

中途另一条口：`voiceState` 常在字幕前回到 `listening`，`VoiceCaptionPacer.markIdle` 清掉尚未消费的 `pendingSpeakingAt`，迟到 ASR 从第一个字重爬。

第十轮：

1. **1 秒静置与 20 秒超时一样先打断**，再发恢复。
2. **恢复后保持静音**，直到新一轮 `speaking`/`responding`（若发出时仍在 speaking，先等 listening 下沿）或**新的** assistant caption id。
3. 被恢复替换的旧 caption id 不再送进开场 reduce、不上台、不锁定宣布 id；`openingTriggerSent && !heardOpening` 时不把下一句宣布当重启。
4. `markIdle` 不再清还未挂到字幕上的 speaking 起点。

语速揭示与「能听见就上台」仍保留。不缓存远端 PCM。

## 后续：第一问之后又说「答辩开始」

2026-08-15 13:41 新 bundle 一场：`9e6b47b8` 在 13:41:29 锁定「嗯,答辩现在开始」并问出第一问，门控打开、400ms 后开麦。`voiceState` 一直是 `listening`。约 17 秒后新 id `e4071db8` 先上台「嗯」，6.5 秒后 ASR 才补成「嗯...答辩现在开始」，此时 `drop=restart` 才打断。`restartSuppressed=1`，但用户已经听见第二句开场。

两处叠加：

1. `applyRemotePlaybackState` 在 `phase === open` 时强制放声，门开之后关不掉音轨；重启守卫要等整句宣布才 `stop_speaking`，拦不住已经送出的 PCM。
2. 开麦发生在第一问还在往外长的时候，委员自己的提问被收成第二轮 bootstrap。

第十二轮：门开后的放声只看 `committeePlaybackEnabled`；用户尚未正经作答时，新的委员字幕 id 从第一个口癖 token 起关音轨并打断。开麦改等锁定开场字幕停更 1.2s。

## 后续：正常问题被短字幕守卫扣住

2026-08-15 15:25 实机日志复现：首问被上游拆成两个 assistant message，第二个 id 从「为什么」继续。`isSuspectedDuplicateOpeningCaption` 复用了「16 字以内都算开场填充」的规则，把「为什么」「为什么作者认为」等正常问题前缀连续判成疑似重复开场。客户端因此关闭远端播放、发送 `stop_speaking` 且不向舞台发字幕；直到文本增长到 16 字才解除，表现为语音已经结束而字幕仍未出现。

第十三轮收窄疑似重复开场判定：只提前拦截纯口癖（如「嗯…」）和正在增长的宣布前缀（如「嗯…答辩」），不再把任意短文本视为填充。多点号口癖统一剥离，仍可在完整「答辩现在开始」出现前保持静音。正常的「为什么」分段会立即上台且不打断音频。

## 后续：疑似拦截本身在制造二次提问与无声无字

2026-08-15 19:55 一场（`openingTriggerSent=false`，全程 `voiceState=listening`）给出完整因果链：19:56:01 第一问字幕 `c998a36c`「好,答辩现在开始。首先,你能用一句话概括……」正常放声；19:56:11 字幕停更 1.2s 后开麦；19:56:14 委员以新 id `0d75eef1` 从「嗯」起说一句正常应答——第十二/十三轮的疑似守卫立刻关音轨、发 `stop_speaking` 并把字幕整条扣住（`drop=restart`）。被打断的模型把这次打断当成用户插话，19:56:16 换新 id `983c3343` 重新宣布「答辩现在开始。第一个问题：……」——首问被再问一遍；而「嗯。」那一条永远没有上台，形成有声无字。旧构建里用户一句「What the fuck」（13 字，过 `isSubstantialUserCaption`）还会解除整个重启守卫，让二次宣布完整放出。

三处叠加：

1. **疑似级拦截在制造它要防的故障。** 口癖开头的后续轮次（「嗯，请讲」「好的，那我换个问法」）是开麦后的正常形态，对它们发 `stop_speaking` 恰好触发模型「被打断 → 重新宣布开场 → 再问第一问」的既观行为；守卫成了二次提问的触发器。
2. **「像样回答」解除宣布式重启抑制。** 宣布句（「答辩现在开始」）在答辩中任何时刻出现都不合法，不应因用户已作答就放行；重问句（「第一个问题:」）反而可能是指代式追问，全场抑制会误伤「关于第一个问题……」。
3. **被扣留后放行的字幕从零爬字。** 门控确认晚于字幕首包时，pacer 以放行时刻起表，文本从第一个字按 7 字/秒揭示，声音却已说到句中，形成整轮恒定几秒的音前字后。

第十四轮：

1. **只拦确认级重启。** 删除 `isSuspectedDuplicateOpeningCaption` 与 `postOpeningHoldId` 扣留机制：口癖前缀、正在增长的宣布前缀照常放声、照常上台；只有完整宣布句式命中（`isDefenseRestartCaption`）或（尚未像样作答时的）显式重问句（`isFirstQuestionReaskCaption`）才关音轨、打断、撤回字幕。确认级拦截最多漏出宣布句开头一两个字，换来后续轮次不再被打断。
2. **宣布式重启抑制全场生效**，不再被「像样回答」解除；重问句抑制仍限首次像样作答之前。被抑制轮次之后的下一条委员字幕恢复放声（`follow-up`）。
3. **字幕携带首包时间。** `VoiceCaption` 新增 `firstDeltaAt`（客户端在该 assistant 首个 delta 到达时打点，随每次发射附带）；`VoiceCaptionPacer` 的新轮锚点取 speaking 标记、首包时间、当前时间三者最早，被门控扣留过的字幕不再从零爬字。

## 后续：乱序字幕快照与重复 patch

重放日志还出现过同一消息长度 `53 → 51 → 55 → 54` 的非单调更新。上游可能重发旧的完整快照，也可能在 DataChannel 重连边界重复同一个 append；如果直接替换/追加，舞台会回退、重复或把下一段声音错配到旧文本。

第十五轮：

1. `VoiceCaptionStream` 对同一消息采用单调文本合并，较短旧快照不再覆盖已收到的内容；同长度快照仍允许修正 ASR。
2. append 带明确但未知的消息 ID 时安全丢弃，等待该消息的完整帧，不猜测另一位说话人的活动流。
3. 连续重放的 append 只保留一次；下一段不同 patch 仍正常追加。下一轮委员进入时清理上一轮 idle 标记，避免新问题在 400ms 后被误刷成全文。

回归覆盖 `VoiceCaptionStream` 的交错 listening patch、显式 ID、乱序快照、重复 append，以及 `VoiceCaptionPacer` 的跨轮 idle 重置。
