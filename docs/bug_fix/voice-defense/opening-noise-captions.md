# 语音答辩开场噪声字幕与委员重启答辩

**状态**：已修复  
**日期**：2026-08-13  
**范围**：ChatGPT Web Voice 答辩间

## 现象

用户尚未说任何话，转写里就出现一条"你"的字幕（如 `a young asian 好的� 解码`，含 U+FFFD 乱码字符）。答辩委员先开始了一段开场，随后话锋一转回复"明白了"，并重新宣布"开始答辩"——像上下文错乱一样把开场重启了一遍。

## 根因

1. **开麦兜底窗口过早放开**：连接初期麦克风上传音轨保持关闭，检测到委员开始响应后恢复；但兜底定时器仅 8 秒。委员首次响应偏慢时，兜底先行放开麦克风，环境声/扬声器串音被上游 ASR 转写成一条"用户发言"。
2. **上游把噪声当成回答**：这条伪造的用户轮次进入模型上下文，委员误以为用户已发言，于是回复"明白了"并重新宣布开始，造成开场重启。
3. **乱码直出**：上游 ASR 对无法解码的音频输出 U+FFFD 替换字符，字幕与转写原样展示。

## 修复

1. `VoiceDefenseClient`：**委员第一句字幕出现之前到达的所有用户字幕整条丢弃**——协议规定委员必须先开场，此前用户不可能已作答，这类字幕只能是上游噪声转写；不上台、不进转写。
2. 开麦兜底从 8 秒延长到 15 秒，缩小"盲开麦"窗口；正常路径仍在检测到委员响应时立即恢复。
3. `protocol.ts` 字幕解析统一剔除 U+FFFD 替换字符。
4. bootstrap 会话规则新增第 7 条：答辩开始只宣布一次，即使出现停顿、杂音或被打断也不得重新宣布或重启答辩——对上游侧的重启行为做提示词层约束。

前两条消除触发源（伪造用户轮次），第四条兜底约束模型行为。均为客户端与提示词改动，不涉及 Host 与信令协议。

## 后续：确认语导致的重复开场

修复噪声触发源后，仍观察到另一种重复开场：委员第一条回复是对注入 prompt 的"确认回执"（"嗯，我明白了。那我就直接问了哈……"，甚至点评材料类型），第二条才按规则宣布"答辩开始"并提问——同一个问题问了两遍。

根因是 bootstrap 只能以普通 user 消息注入（该协议没有可用的 system 通道），模型倾向"先应答、再执行"。提示词层追加两条压制：

1. 规则第 8 条：不要确认收到规则或材料、不要评论材料是什么类型的文档，从第一个字开始保持委员角色；
2. 收口指令改为强约束：第一条回复必须直接以宣布答辩开始的那句话开头，之前不得输出"明白了/好的/收到"之类确认语，也不得先评论材料。

上游模型行为无法保证 100% 遵循，但显式禁止确认语可显著降低复现率。

第二轮迭代后仍观察到"你好，我已经进入审稿模式"式的首回合（禁令措辞已到极限），第三轮改用**字面模板**：收口指令给出首句示例（“答辩现在开始。第一个问题：……”），并显式禁止问候、禁止宣布进入某种模式或角色——模型对示例的服从显著好于对禁令的服从。提示词无法消除“先应答再执行”；后续改为客户端开场状态机，见 [opening-ack-gate.md](opening-ack-gate.md)。根治回执音频本身仍依赖官方 Realtime API 备用后端（真正的 system instructions，见 todo）。
