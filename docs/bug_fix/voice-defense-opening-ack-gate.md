# 语音答辩开场回执把答辩重启

**状态**：已修复  
**日期**：2026-08-13（2026-08-14 补充握手竞态、延迟回执、字幕与计时修复）  
**范围**：ChatGPT Web Voice 答辩间开场门控、总结转写与计时

## 现象

转写预览反复出现同一结构：

1. 委员先回执注入材料（“好的 我已了解背景”），有时紧接着抛出第一个问题；
2. 用户侧出现噪声 ASR（“第一个都是”、`a young asian`、U+FFFD）；
3. 委员把这条噪声当成回答，再宣布“答辩现在开始。第一个问题…”，同一场开场问两遍。

提示词已经禁止确认语、要求首句直接宣布开场，仍稳定复现。

## 根因

这不是文案问题，是开场状态机把错的信号当成“委员已开场”。

ChatGPT Web Voice **没有 system 通道**。会前 brief 只能以 `relay_message`、`author.role = "user"` 注入。模型对 user 消息的默认策略是先应答再执行，所以第一条 assistant 音频几乎总是回执，而不是第一问。

旧门控却是两个过粗的布尔：

- `awaitingInitialAssistant`：DataChannel 上一旦出现 `state === "speaking"` 或任意 assistant 文本，立刻开麦；
- `assistantHasSpoken`：任意委员字幕出现后，就放行用户字幕。

因此回执本身会：

1. 出现在委员字幕里；
2. 打开麦克风；
3. 让扬声器串音 / 环境噪声变成一条 user 轮次；
4. 模型把这条轮次当作用户已经作答，于是重启答辩。

15 秒兜底定时器在委员还在说第一问时也会开麦，放大同一条路径。

## 修复

把开场收成协议层状态机（`createVoiceOpeningState` / `reduceVoiceOpening`），客户端只消费 `phase`：

| 事件 | 门控 |
|---|---|
| 委员回执、短填充、宣布进入某种模式 | 不上台、不进转写、不开麦 |
| 字幕看起来像真正的第一问（宣布开场 / “第一个问题” / 问号或“请你说明”等） | 上台，但麦克风仍关 |
| 委员回到 `listening` / `idle` | 开麦，之后才放行用户字幕 |
| 20 秒兜底 | 仅在委员**没在说话**时放开；若仍在 `speaking` / `responding`，只记下“已开场”，等该轮说完 |

用户字幕在 `phase === "awaiting"` 期间整条丢弃。不再把 `speaking` 或任意 assistant token 当作开场完成。

提示词仍保留“不要确认收到材料、首句直接宣布”，只作上游软约束。根治回执音频本身需要真正的 system instructions（Realtime API 备用后端，见 todo）。

## 回归

`test/voice-defense-protocol.test.ts`：

- “好的 我已了解背景 / 嗯。我 / 进入审稿模式”判定为填充，混合了第一问的长句判定为开场；
- 说话中收到第一问时 `phase` 仍为 `awaiting`，回到 listening 后才 `open`；
- 超时发生在 speaking 时不会开麦，idle 时才会。

## 边界

门控不能取消已经在播的回执音频，只能不让回执变成一次用户轮次。委员若只回执、从不提问，仍依赖 20 秒兜底开麦，避免会话卡死。

## 后续：委员连发两条开场（宣布两次答辩开始）

门控上线后仍复现一种双开场：转写里两条委员消息背靠背、中间没有任何用户轮次——第一条是对注入材料的杂糅回应（“好的,我们开始答辩。你作为作者,先用两句话概括:我的第一个问题:……”），第二条重新宣布（“嗯。答辩现在开始。第一个问题:……”）。最初把它归因于模型对巨型 user 消息的自我修正式二次响应；客户端级事件重放随后确认，稳定触发路径其实是**两段注入握手的竞态**：

1. 委员无视“只回复明白”，首轮直接播出开场和第一问；
2. 音频状态先从 `speaking` 回到 `listening`，最终 `chat_message_delta` 字幕稍后才到；
3. 客户端只凭 `assistantTurnSeen + listening` 就认为首轮是回执，立即补发内部“请开始答辩”；
4. 委员忠实执行这条新指令，于是再次宣布开场。字幕文字守卫此时只能事后 `stop_speaking`，无法撤回已经播放的语音。

公开逆向核实：`conversation_id` 绑定只存在于文本 `backend-api/conversation` 端点，语音 `/realtime/wm` 的 session JSON 没有可用的会话预置或 system 通道，无法把材料静默塞进历史。因此改两层：

1. **两段注入 + 回执确认**（`protocol.ts` + `client.ts`）：bootstrap 收口改为“读完只回两个字：明白”。客户端不再把 `listening` 本身当成回执；只有已经收到“明白/收到/了解背景”等填充回执字幕，并且字幕静置 1 秒没有继续追加时，才发内部触发语“请开始答辩”（消息 ID 与文本进内部过滤，不上台不进转写）。如果状态先到、字幕后到，客户端继续等待；若迟到字幕表明委员已经直接开场，则取消待发触发语。
2. **重复宣布抑制**（`isDefenseRestartCaption` + 客户端守卫）：记录首条开场消息 ID；此后任何不同 ID 的委员消息若以重新宣布开场的句式开头（“答辩现在开始/我们开始答辩/The defense begins”，句首 24 字内、排除“已经/刚才”式引用），立即发送 `stop_speaking` 打断音频，并整条抑制（不上台、不进转写、不参与复盘）。舞台上保留第一条开场的问题。

同时收紧开场期字幕：门控关闭期间只有构成开场的委员字幕上台（宣布或第一问），回执与材料点评一律隐藏；兜底开麦时若从未有字幕上过台，回放最后一条被隐藏的委员字幕，避免空舞台。

## 回归（第二轮）

- `test/voice-defense-client.test.ts` 重放真实竞态顺序 `speaking → listening → 延迟开场字幕`：即使字幕延迟 5 秒也不会抢跑发送第二条触发语；真正的“明白”回执到达并静置后仍会正常拉起开场。
- `test/voice-defense-protocol.test.ts` 验证两次真实会话的双开场文本会判定为重启、普通追问（“回到第一个问题”“我们开始下一个问题”“我们已经开始答辩了”）不误伤；同时覆盖两段注入的中英收口文案、触发语和开场期字幕过滤。

## 边界（第二轮）

`stop_speaking` 仍只能截断、不能消除已经播出的开头一两个字，因此它只保留为最后保险。第二轮方案曾让正常路径等待回执确认；第三轮改为直接开场后，1 秒静置只影响意外纯回执的恢复路径。若始终收不到可识别字幕，仍由原有 20 秒兜底避免会话永久卡死。真正的 system instructions 仍需 Realtime API 备用后端（见 todo）。

## 后续：延迟“嗯，我明白”、字幕省略与提前计时

实机再次出现一条独立委员消息“嗯...明白。”，但本次日志中没有 `[viva] opening trigger dispatched`。这排除了客户端重复补发“请开始答辩”的竞态；真正原因是两段握手的 bootstrap **主动要求模型口头回复“明白”**。实时语音上游可能先生成正式问题，再延迟完成这条确认意图，于是确认语漂到问题之后，形成口癖。

同一轮还暴露两个独立问题：

- 总结页转写正文使用 `line-clamp-2`，长问题被 CSS 强制截成两行并显示省略号，数据本身没有丢失；
- `startedAt` 在 `client.connect()` 前写入，账号会话、WebRTC 与 DataChannel 信令耗时都被计入答辩。实机日志中连接到结束约 48 秒，而指标记录为 62 秒，多出的约 14 秒正是连接等待。

第三轮修复将正常路径改回**单条直接开场**：bootstrap 明确禁止“明白 / Understood”确认回执，第一条响应必须宣布开场并提出第一问。已有的两段逻辑不再是必经握手，只作为模型意外仅回复短确认语时的恢复路径；仍需等字幕静置 1 秒，且直接开场字幕会取消触发。总结页移除逐条字幕的两行裁切；计时在委员首次 `speaking` 时锁定起点，若上游漏发状态则以首条可见字幕兜底，后续事件不会重置。

## 回归（第三轮）

- `test/voice-defense-protocol.test.ts` 断言中英文 bootstrap 不再要求口头回执，首条响应直接开场；
- `test/voice-defense-client.test.ts` 保留回执恢复、延迟字幕与重复开场竞态覆盖；
- `test/voice-defense-timing.test.ts` 验证 connecting 不起表、speaking / caption 首次起表且起点不可变；
- 总结页长字幕不再应用 `line-clamp-2`，完整文本随内容高度展开。

## 后续：无「现在」的「答辩开始」被当成回执，恢复触发再开一次场

转写预览再次出现两条背靠背的委员开场：

1. 「好的，答辩开始。一个问题:你们为什么认为可以完全去掉循环和卷积…复现实验的」（第一问说到一半被截断）；
2. 「嗯,答辩现在开始。第一个问题:论文在Introduction里提到要摆脱 RNN 的顺序计算瓶颈。…」

中间没有用户轮次。这不是字幕省略，也不是 `isDefenseRestartCaption` 认不出第二条——第二条本来就会被判定为重启。真正的触发链是开场检测过窄：

- 开场宣布只认「答辩现在开始」，不认模型常用的「答辩开始」；
- 「好的，答辩开始」去掉空白后不足 16 字，被 `isOpeningFillerCaption` 当成短回执；
- 委员稍一回到 `listening`（第一问说到一半停顿，或 ASR 还在追音频），1 秒静置后客户端发出内部恢复语「请开始答辩」；
- 上游把这条 user 消息当成插话，打断第一问并再宣布一次开场。

抑制侧还有第二个缺口：第二条若先流出「嗯」再长成完整宣布，早期 token 对已打开的门控是合法委员字幕，会先上台；稍后判定为重启时只 `stop_speaking`、不再更新字幕，转写里仍留下这条重复开场。

第四轮修复：

1. **宣布句式对齐**：`答辩开始` / `答辩现在开始` / `我们开始答辩` 以及英文 `the defense begins` 都算开场；「好的，答辩开始」不再走回执恢复路径。
2. **重复开场撤回**：一旦锁定首条开场消息 ID，后续重新宣布的委员消息打断音频，并通过空字幕从舞台和转写里删掉已经上台的那一条（`upsertVoiceCaption`）。

## 回归（第四轮）

- `test/voice-defense-protocol.test.ts`：`好的，答辩开始` 判定为开场而非填充；截图中的第二条判定为重启；空字幕会从列表中撤回。
- `test/voice-defense-client.test.ts`：`好的，答辩开始` 后回到 listening 不会发送「请开始答辩」；两条真实开场字幕只保留第一条，并发送 `stop_speaking`。

## 边界（第四轮）

`stop_speaking` 仍然去不掉已经播出的开头几个字。若委员在用户作答之后用「我们已经开始答辩了」这种引用句，仍不会被当成重启。根治回执音频本身仍依赖 Realtime API 备用后端（见 todo）。

## 后续：开麦后噪声假回答，委员不宣布开场就重问第一问

转写预览出现另一条路径，和第四轮的双宣布不是同一条 bug：

1. 委员：「机制的设计理由是什么？为什么注意力就足以替代循环和卷积网络？」（正经第一问，没有「答辩开始」）；
2. 你：「You So Mmm. Tsk」（口癖 / 环境声 / 回声尾音的上游 ASR）；
3. 委员：「我问第一个问题:论文为什么认为必须去掉循环和卷积…」（重问第一问，仍然没有「答辩开始」）。

中间有一条用户字幕，说明开场门控已经 `open`、麦克风已开。内部触发语「请开始答辩」会被滤掉，不会以这种英文碎片上台。因此这不是恢复触发误发，而是**假回答进入上游上下文 → 模型当作用户已答 → 再问一遍**。

现有守卫压不住：

- 用户字幕只在 `phase === "awaiting"` 时丢弃；门控打开后噪声原样上台；
- `isDefenseRestartCaption` 只认「答辩开始 / the defense begins」，认不出「我问第一个问题」；
- 不能把「第一个问题」无条件并进重启检测，否则会误伤「回到第一个问题，你刚才的回答漏了假设。」；
- bootstrap 第 7 / 9 条只是软约束；藏字幕也撤不回已经进 WebRTC 音轨的音频。

第五轮修复：

1. **应用层抓包**：`VoiceDefenseClient` 对 DataChannel 进出站打 `[viva] wire` 日志（状态、字幕前缀、丢弃原因、开麦、是否发过触发语），结束时打 `wire summary`。不解密 SRTP，bootstrap 全文不落盘。
2. **噪声用户字幕**：`isNoiseUserCaption` 识别口癖词表 / 纯标点 / 短填充；门控已开但尚无像样回答时不上台、不进转写。短答「对」「是」放行。
3. **重问第一问当重启**：`isFirstQuestionReaskCaption` 认句首「我问第一个问题 / 第一个问题: / First question:」，前缀排除「回到 / 下一个」。仅在已锁定开场且尚无像样用户回答时 `stop_speaking` 并撤回字幕。
4. **开麦尾音**：`phase` 切到 `open` 后延迟 400ms 再使能麦克风轨，避开委员音频尾与 AEC 收敛。不发送「刚才是杂音」之类内部 user relay。

## 回归（第五轮）

- `test/voice-defense-protocol.test.ts`：`You So Mmm. Tsk` 为噪声，「对」/含汉字短句不是；截图中的「我问第一个问题:…」为重问，不是 `isDefenseRestartCaption`；「回到第一个问题，你刚才…」仍不是重启。
- `test/voice-defense-client.test.ts`：重放截图三条字幕后舞台只留第一问并发送 `stop_speaking`；用户正经作答后的追问仍上台；门控打开后 400ms 内麦克风保持关闭。

## 边界（第五轮）

字幕过滤不能阻止上游已经听到的噪声音频，只能挡住转写并打断随后的重问。若 400ms 延迟后仍稳定出现高能量噪声，需要另做 VAD，不在这一轮做。

## 后续：开场前奏提问仍从扬声器播出

第五轮之后仍能听到：委员先讲一大段像提问的话，再说「答辩开始，第一个问题是……」。这不是噪声假回答，也多半不是「请开始答辩」误发。

根因是 bootstrap 只能当普通 user 消息注入。模型先按材料提问（规则 1 / 4），再补一句开场模板。客户端此前只藏字幕、不关远端播放，所以前奏仍然出口。开场检测把「带问号的第一问」也当成 `heardOpening`，麦克风还会在宣布之前打开。

第六轮：在听到宣布句式（`答辩开始` / `the defense begins`）之前保持委员远端音频静音（音轨 `enabled=false` + `<audio muted>`）。问句形前奏不上台，长到 16 字后 `stop_speaking` 截掉，委员回到 listening 再发内部「请开始答辩」。**真正开场的那一轮在 `speaking` 一开始就放声**，字幕只在放声之后跟着流式出现，避免等 ASR 认出「答辩开始」才开扬声器——那样声音已经说到后半句，字幕却整段倒出来，音话错位。同一句里先宣布的情况仍在字幕命中时开声。20 秒兜底仍会开声，避免永远静音。

## 回归（第六轮）

- `test/voice-defense-protocol.test.ts`：无宣布的「机制的设计理由是什么？…」开场期不上台，也不把 `heardOpening` 置位；「答辩现在开始。第一个问题：…」才算宣布。
- `test/voice-defense-client.test.ts`：前奏提问期间远端音轨关闭并发送 `stop_speaking`；催开场之后的下一轮 `speaking` 立刻开声，此时舞台仍无字幕，宣布字幕随后跟上；噪声重问夹具改为先带「答辩开始」再开麦。

## 边界（第六轮）

字幕晚于音频是上游 ASR 的固有延迟，开场轮从 `speaking` 起同时放声和收字幕，二者保持同一轮。`stop_speaking` 截不断已经送出的前奏 PCM。没有宣布、只有提问时依赖 20 秒兜底或恢复触发，不会一直无声。

> 第六轮的 `speaking` 提前放声和 20 秒盲放开策略已由下述第七轮替换。

## 后续：20 秒盲兜底把上一轮字幕配到了下一轮声音

打包版实机会话给出了可重复的证据链：15:36:07 连接成功，15:36:27 恰好在 20 秒看门狗到期时记录 `committee playback enabled reason=gate`；结束摘要为 `openingTriggerSent=false`，同一时段没有 `offline`、WebRTC `disconnected/failed` 或 DataChannel 错误。保存的转写依次出现：

1. 「好的，我们来聚焦他们的核心主张。我想问……」；
2. 「嗯。答辩现在开始。第一个问题：……」。

这不是一次普通的网络卡顿。旧状态机把“时间到了”当作“已经听到开场”的证据，直接将门控设为 `open`；`applyOpening` 又把 `lastHiddenOpeningCaption` 回放到舞台，同时打开仍在继续的远端音频。因此屏幕显示的是缓存的上一轮文字，扬声器可能已经处于下一段声音，形成跨轮声画错配。之后宽松的宣布检测还会接受带「嗯」前缀的恢复轮。

第七轮改为 fail-closed：

1. 只有字幕从第一个字起命中「答辩现在开始」或 `The defense begins now` 才是合格开场；「嗯。答辩现在开始」「好的，答辩开始」仅用于识别异常/重启，不会开声、上台或开麦。
2. 20 秒到期不再伪造 `heardOpening`，也不回放任何隐藏字幕；客户端无条件 `stop_speaking` 打断旧轮次，再发送要求精确首句的内部恢复指令。恢复后再超时则显示本地化错误，不把未知内容漏给用户。
3. 删除恢复轮 `speaking` 一到就提前开声的旁路。远端音轨和 `<audio>` 只有在规范开场字幕命中后才启用，字幕与声音至少来自同一个委员消息。
4. 通话计时不再由连接、上游 `speaking` 或先到字幕触发，而由 `onCommitteePlayback(true)`——即委员声音真正获准播放的时刻——触发且只触发一次。

## 回归（第七轮）

- `test/voice-defense-client.test.ts` 重放上述真实首轮：20 秒超时后仍为 `awaiting`、舞台无字幕、远端音轨关闭，并验证打断与精确恢复指令；后续「嗯。答辩现在开始」仍不能放声。
- `test/voice-defense-protocol.test.ts` 验证超时本身永远不能证明开场已发生，且中英文规范前缀通过、带口癖前缀和宽松改写失败。
- `test/voice-defense-timing.test.ts` 验证只有远端播放启用才起表，连接等待与重复播放通知不改变起点。

## 边界（第七轮）

远端声音使用 WebRTC RTP，流式字幕使用 DataChannel，当前私有协议没有提供两者共享的逐字时间戳；即使连接健康，抓包也观察到字幕增量间隔约 3.6 秒。网络抖动可能放大字幕的 token 级延迟，但不能解释本次“上一轮字幕 + 下一轮声音”的稳定错配。第七轮消除了跨消息错配；在不缓存并重放整段远端音频的前提下，不承诺卡拉 OK 式逐字同步。
