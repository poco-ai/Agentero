# 大论文库阅读时长性能验证

## 环境与数据

2026-11-12，在 Windows 开发机的实际 Tauri Host + WebView2 中测试。CPU 为 Intel Core i5-13600KF（14 核 / 20 线程），内存 32 GiB，WebView2 Chromium 157。应用为开发构建，正式版同时运行；结果不能直接推断低配置机器或 release 构建性能。

两档数据均为独立临时 Vault 的**合成目录元数据**，没有生成或打开 1,000 / 10,000 个真实 PDF。每天为每篇写入 `paper.blur` 和重复 `paper.session`，覆盖 30 天，并混入另一 Vault 的记录以检查隔离；原始事件为每篇 10 条。直接填充 catalog，表格仍通过产品的 `paper_list` IPC 加载。

| 论文数 | 日聚合行数 | 原始事件数 | 天数 |
|---|---:|---:|---:|
| 1,000 | 66,000 | 10,000 | 30 |
| 10,000 | 660,000 | 100,000 | 30 |

对每个规模分别启动新 Host / WebView2，测原实现和新增索引后的实现。窗口为 1440 × 900；系统 DPR 在两次测试间由 1.5 变为 1.25，因此不把 UI 或内存差值归因于索引。IPC 测量包含 Host 打开数据库、保留策略、聚合、序列化及前端接收。首次记录是启动完成后的第一次测量，**不是操作系统冷缓存或首次建索引耗时**。

## 结果

每组聚合 IPC 连续调用 31 次，检查返回恰好当前 Vault 的全部论文，抽查首 / 中 / 末论文为 `30 × 单日毫秒数`，没有重复累计 `paper.session` 或其他库记录。

| 规模 | 实现 | IPC 中位 ms | IPC P95 ms | 本轮首个 IPC ms |
|---|---|---:|---:|---:|
| 1,000 | 原实现 | 41.3 | 49.3 | 40.2 |
| 1,000 | 索引后 | 20.0 | 24.3 | 19.0 |
| 10,000 | 原实现 | 356.5 | 440.3 | 1,028.8 |
| 10,000 | 索引后 | 141.6 | 166.1 | 147.3 |

实际挂载的 Library 中调用完整目录刷新 10 次，等待两帧；点击阅读时长列升 / 降序 12 次，等待两帧并校验首行。以下是索引后结果；完整刷新包含既有 catalog 读取和本地 PDF 能力探测，不是单独的阅读时长开销。

| 规模 | 完整目录刷新中位 / P95 ms | 升降序中位 / P95 ms | 可见 DOM 行 |
|---|---:|---:|---:|
| 1,000 | 218.4 / 285.2 | 75.5 / 138.7 | 23 |
| 10,000 | 1,427.0 / 1,676.9 | 313.3 / 381.4 | 23 |

没有捕获页面异常，排序结果正确，虚拟表没有挂载全部论文。10,000 篇完整刷新仍超过 1 秒；本轮未改变全库加载、PDF 能力探测或前端排序结构。

完成上述循环时，1,000 / 10,000 篇的 JS 已用堆约 95.6 / 228.7 MiB，Host 工作集约 71.4 / 77.0 MiB，Host 与其 WebView2 子进程工作集之和约 856 / 1,234 MiB。工作集求和含共享页面，开发构建还有模块和调试开销；这是一次使用后的快照，不能用作最低内存要求或泄漏判断。

## 优化与回归

原 SQL 执行计划是 `SCAN usage_daily` 加 `USE TEMP B-TREE FOR GROUP BY`。新增幂等的部分索引：

```sql
CREATE INDEX IF NOT EXISTS idx_usage_daily_reading
ON usage_daily(vault, paper_path, dur_ms)
WHERE kind = 'paper.blur' AND paper_path != '';
```

它只保存有效阅读聚合，按 Vault / 论文顺序提供时长；查询不再需要临时分组排序。旧 schema v1 数据库首次打开也补建，不丢弃或重写时长，不改变 IPC 契约。首次补建需要扫描既有聚合并占用索引磁盘空间，本轮没有测首次迁移的冷启动开销。

新增回归先在原实现失败：旧库重开仍全表扫描并临时排序。修复后检查旧数据可读、指定索引被使用且没有临时 B-tree；17 项 Rust usage 测试全部通过。5 个前端文件的 32 项计时、刷新、排序及设置测试通过。

## 复测方式

1. 在临时 Vault 复制一份 catalog / usage schema，批量插入上表规模的合成数据；`vault` 字段必须使用 Host 实际打开后的规范路径。
2. 用独立 identifier、XDG 数据目录及 WebView2 profile 启动 `pnpm tauri dev`，打开 Library，等待 catalog 论文数稳定。
3. 通过桌面 WebView2 的 CDP，在页面中计时实际 IPC，而不是在普通浏览器中 mock Host：

   ```js
   const start = performance.now();
   const response = await window.__TAURI_INTERNALS__.invoke(
     "usage_reading_durations", { args: { vault } },
   );
   const elapsedMs = performance.now() - start;
   ```

4. 每次都断言论文数量、累计时长及其他库隔离，保留所有样本后计算中位 / P95。完整刷新和排序要等待下一次实际绘制，并检查顺序及 DOM 行数。
